# Что я бы улучшил в v2.0 и почему

Список отсортирован по отношению «польза / стоимость». Для каждого пункта —
проблема, варианты и почему выбран именно этот.

## 1. Зрение: детектор элементов вместо OCR+эвристик

**Проблема.** `Windows.Media.Ocr` даёт текст, UI Automation — дерево, но Canvas,
Flutter, игры и нестандартные веб-компоненты не видны ни там, ни там. Сейчас в
таких местах агент падает на скриншот в LLM и координаты «на глаз».

**Варианты:**
- (а) ONNX Runtime + OmniParser/UI-детектор — точные боксы всех кликабельных
  элементов, работает офлайн, +~150 МБ моделей и +40-80 мс на кадр;
- (б) PaddleOCR/Tesseract — лучше только текст, элементы не решает;
- (в) полагаться на vision-LLM — уже сделано, но это ~1500 токенов и 1-3 с на шаг.

**Выбор: (а)** как второй источник элементов, с фолбэком на (в). Модель качается
при первом использовании, а не лежит в `.exe` — иначе теряем «один файл».

## 2. Память: гибридный поиск (BM25 + эмбеддинги)

FTS5 не находит «оформить заказ» по запросу «купить». Колонка `embedding BLOB`
в схеме уже зарезервирована. План: `sqlite-vec` + локальные эмбеддинги
(bge-m3 через ONNX), ранжирование `0.6*bm25 + 0.4*cosine`. Векторная БД
(Qdrant/Chroma) отвергнута: отдельный сервис против требования «один .exe».

## 3. Дешёвая модель на рутину, дорогая на решения

Сейчас каждый шаг идёт в одну и ту же модель. 80% шагов — «нажми очевидную
кнопку». Роутер уже знает `purpose` каждого запроса, осталось повесить на него
маршрутизацию: `act` → дешёвая vision-модель, `plan`/`reflect` → сильная.
Экономия по моим прикидкам 5-8x по деньгам при том же результате.

## 4. Кэш «экран → действие»

Повторные сценарии (тот же Ads Manager каждый день) проходят один и тот же путь.
Хеш UI-дерева + подзадача → сохранённое действие. При совпадении шаг выполняется
без обращения к LLM: 0 токенов, ~10 мс вместо ~2 с. Инвалидация — по первому же
несовпадению результата.

## 5. Запись и воспроизведение сценариев

Успешно выполненная задача сохраняется как параметризованный скрипт. «Залей отчёт
в Field» на 20 объектов должно стоить один прогон LLM, а не двадцать.

## 6. Прозрачное восстановление после сбоев

Сейчас падение приложения посреди задачи теряет прогресс. Нужен журнал шагов
(таблица `steps` уже есть) + возобновление с последнего успешного шага после
перезапуска, с проверкой, что экран всё ещё тот.

## 7. Песочница и политика прав

Сегодня защита — закрытый enum действий и подтверждение необратимого. Стоит
добавить явный файл политик: белый список доменов/приложений, лимит трат
(«не тратить больше N тенге без спроса»), запрет на действия вне рабочих часов.

## 8. Наблюдаемость

Локальная страница со статистикой: сколько шагов, стоимость по провайдерам,
где чаще всего ломается, какие уроки реально сработали. Данные для этого уже
пишутся (`steps`, `lessons.success`), не хватает отображения.

## 9. Мультиэкран и DPI

Захват сейчас корректен для основного монитора. Нужны: выбор монитора,
per-monitor DPI v2 и координаты в виртуальном рабочем пространстве.

## 10. Android: scrcpy-канал вместо screencap

`screencap` — 200-400 мс на кадр. Для задач вроде «пролистай ленту и проанализируй»
это узкое место. scrcpy-сервер даёт видеопоток и ввод с задержкой ~30 мс.

## 11. Параллельные задачи

Один агент — один экран. Для фоновых задач нужны отдельные Windows-сессии
(RDP-сессия или второй пользователь), иначе агент дерётся с человеком за курсор.

## 12. Подпись и автообновление

Неподписанный `.exe` ловит SmartScreen. Нужны code signing сертификат и
дельта-обновления вместо полной замены бинаря.
