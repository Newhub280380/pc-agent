# JEV: что уже интегрировано, что измерено, что улучшено

Короткий ответ на вопрос «можно ли встроить JEV Type safe в агента и как сделать
его быстрее, умнее и без галлюцинаций»: **можно — и уже встроено**. Ниже карта по
коду, найденные слабые места, изменения этой ветки и измерения.

## 1. Три уровня JEV, которые уже есть

| Слой | Файл | Что решает | Цена | Детерминизм |
|---|---|---|---|---|
| Локальный байесовский фильтр | `core/src/jev.rs` | «класс действия исторически успешен?» (успехи/провалы из журнала шагов, минимум 3 наблюдения) | микросекунды, офлайн | полный (чистая арифметика) |
| Модель `typesafe/jev-1.13` | `core/src/decisions.rs` | `noul` — да/нет с вероятностью; `choice` — выбор ветки из готовых вариантов | сеть + инференс, таймаут 8 с, кэш по каноническому JSON | ответ модели — нет; решение — да (порог + кэш + квантование) |
| Шлюз маршрута (MCP) | `core/src/jev_gate.rs` (2 961 строка) | маршрут из каталога операторов, свидетели с SHA-256, закрытие шага только по наблюдению шлюза, печать back gate, `jev_report` | без LLM в точках решения | полный: решение принимает код + Z3 |

Вокруг них — то, что действительно убирает галлюцинации: `logic.rs` (Z3 проверяет
инварианты и порядок шагов), `grounding.rs` (пути/кнопки/ссылки из ответа модели
сверяются с наблюдением до действия), `verify.rs` (Do → Verify → Report, `Unknown`
успехом не считается), `corpus.rs`/`ledger.rs` (каждое утверждение отчёта — с
цитатой, проверенной по тексту источника).

Честная карта точек решения — `docs/hard-loop-audit.md`: там 14 точек и указано,
где LLM остаётся датчиком, а где судьёй. Это уже уровень «type safe decisions», к
которому стоит относиться как к факту, а не к плану.

## 2. Что было не так (найдено в коде этой ветки)

| № | Проблема | Где |
|---|---|---|
| 1 | Модель спрашивали на **каждом** шаге — до локальной статистики, до grounding, блокирующим `ureq` с таймаутом 8 с | `agent/mod.rs`, блок `if self.decisions.enabled()` |
| 2 | Её «нет» на обратимом шаге **игнорировалось** («сомневается, но шаг обратимый — делаю») — платили задержкой за сигнал, который выбрасывали | там же |
| 3 | Один порог 0.6 на всё: 0.61 — это «да» и для «клик по вкладке», и для «Оплатить» | `decisions.rs`, `YES_AT` |
| 4 | Дрожь третьего знака: 0.601 и 0.604 давали разные решения, хотя это один ответ | там же |
| 5 | Кэш только в памяти процесса и без границ: после перезапуска тот же вопрос снова уходит в сеть, за долгий прогон растёт без предела | `decisions.rs`, `BTreeMap` |
| 6 | Сеть упала → предупреждение и шаг идёт, в том числе необратимый | `agent/mod.rs`, `warn_jev` |
| 7 | В `state` уходят только `action`, `goal`, `failures` — ни свидетелей шлюза, ни хэша экрана, ни OCR. Модель судит по формулировке, а не по наблюдению | `agent/mod.rs` |
| 8 | Предзагрузки нет: необратимый шаг всегда ждёт сеть в критическом пути | — |

## 3. Что изменено в этой ветке

Новый модуль `core/src/decision_policy.rs` — правила «когда спрашивать модель и
как читать ответ». Он не заменяет шлюз, Z3 и grounding, а ставит их в правильном
порядке относительно сети.

| | Было | Стало |
|---|---|---|
| Порядок | сеть → локальная статистика → grounding | локальная статистика → (сеть только для необратимого) → grounding |
| Обратимый шаг | запрос к модели, ответ игнорируется | без сети, микросекунды; источник подписан |
| Необратимый шаг | порог 0.6 | планка 0.75: «скорее да» не считается подтверждением |
| Точность вероятности | сырое `p` | квантование до сотых, полоса 0.6 / 0.4 |
| Сеть упала | шаг идёт молча | вето на необратимый шаг (одна попытка), затем подтверждение человеком |
| Кто решил | не видно в журнале | `локальная статистика` / `jev-1.13` / `запасное правило` / `проверка выключена` |
| Управление | — | `PCAGENT_JEV_MODE=tiered` (по умолчанию), `always` — прежнее поведение, `off` — только локально |

Подключение — `mod decision_policy;` в `main.rs`, поле `policy` в `Agent` и замена
двух разрозненных блоков в цикле на один вызов `policy.decide(...)`
(`core/src/agent/mod.rs`). Шлюз, Z3, grounding, verify и пороги локального `jev.rs`
не тронуты.

## 4. Измерения

`tools/jev_eval.py` — стенд: 20 размеченных шагов (обратимые навигационные,
необратимые с подтверждением и без, «серая зона» 0.60–0.75), две политики на одном
наборе, проверка свойств (код возврата 1 при нарушении).

Отчёт офлайн-прогона: [`docs/jev_eval_mock.md`](jev_eval_mock.md). Ключевое:

| Метрика | baseline (модель на каждом шаге) | tiered (эта ветка) |
|---|---:|---:|
| Сетевых вызовов на шаг | 1.00 | 0.40 |
| Задержка шага p50 | 398 мс | 0 мс |
| Опасных (необратимых) шагов разрешено | 1 | 0 |
| Переключений решения от дрожи ±0.004 | 184 из 400 | 0 из 400 |

**Честная оговорка.** Это режим `mock`: роль модели играет синтетический
ответчик, поэтому числа показывают свойства политики (сколько вызовов, как
читается вероятность, что делает вето), а не качество `jev-1.13`. Задержка
модели — допущение 420 мс. Реальные числа даёт только `--live`:

```bash
OPENROUTER_API_KEY=... python3 tools/jev_eval.py --live --repeats 5 \
    --out docs/jev_eval_live.md
```

Второй эффект виден в таблице расхождений: политика отказывает в шаге
«Оформить заказ» при вероятности 0.68 (человек подтвердит — это один шаг) и
блокирует «Отправить» при предупреждении на экране при 0.70. Прежний порог 0.6
пропускал второй молча.

## 5. Дальше по приоритету

1. **Персистентный кэш решений** (`decisions.rs`). SQLite-таблица
   `decisions(key, kind, payload, created_at, hits)`, ключ — тот же канонический
   JSON, TTL, лимит строк. Эффект: повторный прогон не платит сетью, ответ не
   меняется между запусками. Проверка: `cargo test decisions`, затем два прогона
   одной задачи — `cache_hits > 0` во втором.
2. **Состояние с доказательствами** (`agent/mod.rs`). В `state` добавлять
   `witness_id`, SHA-256 экрана/файла, счётчик grounding-нарушений. Модель начнёт
   отвечать по наблюдению: «действие опирается на эти факты?». Это главный
   оставшийся источник «умных, но необоснованных» ответов.
3. **Батчинг вопросов** (`decisions.rs`). `questions` — это map; один запрос может
   спросить `noul` и `choice` сразу для двух кандидатов. Экономия — один RTT на
   шаг, где есть выбор.
4. **Replay-режим** (`PCAGENT_DECISION_REPLAY=файл`). Прогон задачи без сети по
   записанным решениям: воспроизводимость и разбор инцидентов байт-в-байт.
5. **JEV как ранжировщик, а не судья.** Для `choice` подавать только кандидатов,
   уже прошедших Z3 и каталог операторов, и брать `confidence` как порядок, а не
   как разрешение. Тогда модель не может «выбрать» несуществующий шаг.
6. **Телеметрия решений** (`ledger`/`state`): писать `source`, `p`, `ms` каждого
   вердикта. Без этого нельзя ответить «сколько стоил JEV в этой задаче».
7. **Калибровка порогов по данным.** Собрать ≥200 решений с известным исходом и
   подобрать `YES_AT` / `IRREVERSIBLE_AT` по precision/recall, а не на глаз.
   Менять константы только после этого.

## 6. Честные пределы

* **Сборки здесь нет.** В песочнице нет `cargo`, а сеть закрыта для
  `static.rust-lang.org` и `crates.io`. Форматирование проверено настоящим
  `rustfmt`; компиляция и тесты — задача CI (`linux-core`: `cargo fmt --check &&
  cargo test`).
* **Модель недетерминирована по природе.** Детерминизм даёт не `jev-1.13`, а
  обвязка: кэш, квантование, запрет переспрашивать, replay. Обещать «модель
  всегда отвечает одинаково» нельзя — можно обещать «решение не меняется».
* **«Без галлюцинаций» — это про проверку, а не про модель.** JEV решает
  «делать/не делать», а «что правда» решают свидетель, Z3, grounding и verify.
  Модель может ошибиться в вероятности; соврать в отчёте ей не даёт код.
* **Mock-числа не заменяют замер на вашей машине** и вашей модели.

## 7. Как проверить

```bash
cd core
cargo fmt --check
cargo test decision_policy -- --nocapture   # правила политики
cargo test decisions                        # кэш, секрет, разбор ответа

cd ..
python3 tools/jev_eval.py --mock                       # свойства политики
OPENROUTER_API_KEY=... python3 tools/jev_eval.py --live --repeats 5  # реальные числа
```

Живой прогон задачи: `PCAGENT_JEV_MODE=always` возвращает прежнее поведение,
`off` — полностью локальные решения, `tiered` (по умолчанию) — эта ветка.
